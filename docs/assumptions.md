# 実装時の前提・決定事項

指示書23章・22章の方針（「勝手に固定的な業務ルールを作らず、仮定を一覧にして質問する」）
に沿って、実装中に決めた前提と、利用者に確認して決定した事項をまとめます。

## 開発プロセスの決定事項

### 利用者によるChrome確認手順のリスク別運用（B案）

実装時間短縮のため、「実装後に利用者へ提示するChrome上での確認手順」を、変更の
性質によって以下のように使い分ける（利用者の承認済み）。

- **データに触れる変更**（Excel解析・自動判定ロジック、保存・復元、学校別書式
  設定、学級プロファイル、将来の生成ロジック等）: 従来どおり、実装後に詳細な
  確認手順を提示し、利用者の実機・実データでの確認を経てから次の項目へ進む。
  理由: このアプリの不具合はこれまで実際に、file://特有の挙動・実際のOS操作・
  利用者の既存データとの組み合わせでのみ再現するものが複数あった（ドラッグ＆
  ドロップの読み込み不具合、キャッシュされた古いマッピングが残る不具合等）。
  自己チェック（Playwright）はまっさらな状態からの機械的な検証のため、これらの
  死角を埋められない。
- **表示・追加のみで、データの読み書きやExcel解析ロジックに一切触れない変更**
  （文言表示の追加、UIの案内メッセージ、既存動作に影響しない純粋な追加機能等）:
  実装後の自己チェック（Playwright）のみで完了とし、詳細な確認手順の提示・
  利用者確認待ちは省略する。壊れた場合の実害が小さく（Git履歴からすぐに切り
  戻せる）、利用者確認で発見できる情報量も限定的なため。複数件をまとめて、
  後日まとめて簡単に見ていただく形にする。
- どちらに該当するか迷う場合は、安全側（データに触れる変更として扱う）に倒す。

1. **複数校での利用は当面想定しない**。学校別書式設定（自動判定のマッピング）は
   ファイル種別ごとに1つだけ保存する、現在の設計のままとする。複数校での利用が
   必要になった時点で、保存キーに学校ID（または学校名）を追加する設計変更を行う。
2. **授業時数･下校予定時刻ファイルで同じ月に複数の改訂版シートがある場合、
   自動採用はしない**。マッピング画面で、月ごとに「どのシートを使うか」を
   プルダウンから毎回明示的に選ぶ方式に変更した（候補が1つしかない月は
   自動的にそれを使う。2つ以上ある月だけ、選択肢を空欄から選ばせる）。
3. **固定時間割ファイル内の「分科計画」表**（５年２組以外の学級の分科担当・時数も
   含む一覧）は、確認画面には不要と判断し、検出自体を削除した（旧版では「保持する」
   としていたが、これは撤回して削除が最新の決定）。
4. **「総合的な学習の時間」のように1シートに複数の単元系列が並ぶ教科**には、
   専用の検出ロジックを追加した。シート内の「【系列名】」という角括弧見出しを
   系列の区切りとして自動検出し、系列ごとに単元名・計画時数の候補列を提示する
   （実データでは3系列を正しく検出）。角括弧見出しが無い教科では、従来通り
   1系列として扱う。この自動検出でも拾いきれない系列がある場合に備えて、
   マッピング画面に「手動で項目を追加」欄を用意し、シート・項目名・セル範囲を
   指定して任意の項目を追加できるようにした（削除も可能）。
5. **授業時数･下校予定時刻.xlsx と R8固定時間割.xlsx は、年間を通じて随時更新
   される資料として扱う**。この2つは、取込み画面の同じ枠に新しいファイルを
   取り込み直すだけで、いつでも最新版に差し替えられる（既存の取込み機能で
   対応済み。表の形が変わった場合は自動解析結果の確認画面で警告する）。
   取込み画面には、取り込んだ日時を表示し、この2ファイルには「随時更新される
   資料」である旨の説明を追加した。フォルダ監視のような自動取り込みは、
   ブラウザから毎回フォルダへのアクセス許可が必要になり操作が煩雑になるため
   採用せず、手動での取り込み直しのみとしている。

## フェーズA動作確認後の仕様修正（2巡目）

利用者による試用の結果を受けて、以下を修正した。

- **画面の流れ**: ①利用者・担当学級設定を保存すると、選択操作を挟まず自動的に
  ②ファイル取込みへ進むようにした。
- **ファイル取込み**: 各ファイル枠にドラッグ＆ドロップで直接ファイルを渡せるように
  した（ファイル選択ボタンに加えて、枠全体がドロップ先になる）。
- **自動解析結果の確認・対応付け**:
  - 確認の手間を減らすため、シートプレビュー機能を追加。各項目の「範囲」欄の
    「表示」ボタンを押すと、実際のシートの内容を画面内に表示し、該当セル範囲を
    黄色でハイライトする。サンプル値の文字列だけでなく、シートの実物を見て確認
    できる。
  - すべての項目が高い確度で判定できたシートは、既定で折りたたんで一覧性を上げ、
    「すべて確認済み（n件） - 詳細を見る」から展開できるようにした。確度が低い・
    未検出・選択が必要な項目が1つでもあるシートは、常に展開表示する（簡素化しても
    確実性は落とさない）。
  - 出力先ひな型の「教科名 / 単元名」欄には、教科名だけでなく行事名や
    「○○先生の案による」といった分科担当者の記載が混在することを明記し、
    これはエラーではなく仕様通りの内容であることを画面に注記した。
  - 出力先ひな型の「予定表」シート（年度・学級名・月別教科別予定時数）は、
    アップロード前に利用者が入力を終えている前提の資料のため、確認画面には
    表示しないことにした（検出自体を行わない）。
  - 授業時数･下校予定時刻の確認画面には、担当学級の学年の列だけを表示し、
    他学年の列は表示しない（利用者情報で登録した学年をもとにフィルタする）。
  - 年間指導計画の確認画面には、利用者情報の「分科教科と担当者」に登録した教科
    （担任以外が受け持つ教科）のシートを表示しない。その教科の単元進度は、
    将来のフェーズC（分科資料の取込み）で分科担当者自身の資料から取り込む想定。

## フェーズA動作確認後の仕様修正（3巡目）

2巡目の修正を試用いただいた結果、以下を修正した。

- **キャッシュの陳腐化を検知する仕組みを追加**: 「授業時数･下校予定時刻の表示が
  担当学年だけにならない」という報告の原因は、確定済みのマッピングをファイルの
  指紋（フィンガープリント）が一致する限り再利用する仕組みが、アプリ側の判定
  ロジックの更新を考慮していなかったことだった。判定ロジックにバージョン番号
  （`DETECTOR_VERSION`）を持たせ、保存済みのマッピングがそれより古い場合は
  ファイルの中身が同じでも「判定内容が更新された」とみなして再計算・再確認を
  促すようにした。今後、判定ロジックを修正するたびにこの番号を上げる運用とする。
- **②ファイル取込み完了後、③へ自動で進む**ようにした（5つすべて取り込まれた
  時点で自動遷移）。
- **ドラッグ＆ドロップの読み込み不具合**: 見た目の反応はあるのに読み込まれない
  現象への対処として、`dataTransfer.files`が空の場合に`dataTransfer.items`から
  ファイルを取り出すフォールバックを追加し、それでも取得できない場合は
  「読み取れませんでした」という明確なエラー表示に変えた（無反応のまま終わらせない）。
  実際のOSからのドラッグ＆ドロップ特有の挙動は開発環境では完全には再現できないため、
  改善後も症状が残る場合は教えてほしい。
- **シートプレビューの見た目を改善**: 結合セルをExcel同様にcolspan/rowspanで
  描画し、数値は右寄せにするなど、実際のシートに近い見た目にした。
- **シートプレビューの表示位置**: 画面上部固定をやめ、確認項目一覧（左）と
  プレビュー（右、スクロールしても追従する固定表示）の2カラムに変更した。

## 別紙「フェーズ1プロトタイプ 優位性強化・脆弱性低減 実装指示書」への対応（4.1）

利用者から別紙を受領し、3章の現状診断を実施した上で、優先度1のうち **4.1 変更前スナップショットと復元** を実装した（利用者の承認済み）。

- バックアップの書き出しに`schemaVersion`・`appVersion`（`src/storage/backup.ts`）・`exportedAt`を持たせた。
- 復元前に、渡されたJSONの構造を検証し（`validateBackupPayload`）、1件でも想定外の形式があれば**一切書き込まずに**エラー表示する。壊れたバックアップ・空ファイル・配列でないデータ・idの無いデータをそれぞれ拒否することを実データで確認済み。
- 復元を実行する直前に、現在のデータを自動的に別ファイルへバックアップする（ダウンロードされる）。
- 復元直後は、同じセッション内であれば「直前の状態に戻す」ボタンで即座に戻せる（ページの再読み込みまでの間のみ有効。再読み込み後はダウンロード済みの自動バックアップファイルから手動で復元する）。
- 旧形式（`backupVersion`のみでschemaVersionが無いバックアップ）も読み込めることを確認済み（後方互換）。

**動作確認中に見つかった、今回の変更とは別の既存仕様**: 復元は現在、**IDが一致するレコードを上書き・追加するだけで、バックアップに存在しないレコードを消さない「マージ」動作**になっている（`storage/db.ts`の`importAllData`は元からこの仕様）。そのため、例えば「学級Aの設定だけを含むバックアップ」を復元しても、既存の学級Bの設定は消えずに残る。

**この挙動について利用者に確認し、マージ方式を維持することで決定した**。利用者の実際の使い方（基本的に自分の学級のみを扱い、他人の学級を作成することは稀）を踏まえると、「バックアップの内容だけに完全に置き換える」方式（フルリプレイス）は、滅多にバックアップに含めない「他人の学級」のデータを、無関係な復元操作で気づかないうちに消してしまうリスクがある。一方マージ方式は、使わなくなった学級がバックアップに存在しない場合でも消えずに残る（＝不要なデータが残留する）だけで、データ消失の方向には倒れない。安全側に倒すため、マージ方式を維持する。

マージ方式の副作用（不要になった学級が残り続ける）に対応するため、**学級プロファイルの削除機能**を追加した（`storage/repository.ts`の`deleteClassProfile`は元から用意されていたが、UIから呼び出す経路が無かった）。①利用者・担当学級設定画面の「登録済みの学級から切り替え」の下に「この学級を削除する」ボタンを設置し、確認ダイアログを経てから削除する。削除対象は学級プロファイル（`classProfiles`）のみで、取り込み済みファイル・学校別書式設定（ファイル種別ごとの共有データで学級に紐付いていない）には影響しない。削除した学級が選択中だった場合は、残っている学級の1件目に自動的に切り替わり、登録済みの学級が0件になった場合は入力欄を空の状態に戻す。

## 別紙4.2対応：ファイル取込み時の事前検査

実装順どおり、4.1の次に4.2を実装した（利用者の承認済み）。

- `src/excel/fileValidation.ts`を新設。取込み前に、空ファイル・50MB超の
  ファイル・先頭バイトがxlsx/xlsm(zip)ともxls(OLE2)とも一致しないファイルを
  拒否する（解析処理自体を呼ばない）。
- 解析が例外を投げた場合は、メッセージを分類して日本語で説明する
  （パスワード保護／破損／未対応形式／その他、の4分類＋元エラー内容の併記）。
- 解析には成功したがシートが1枚もない、またはシート数が異常に多い
  （200枚超、実データは最大32枚程度）場合も、保存前に中止する。
- シートの実サイズがサンプリング上限（400行×60列）を超えていた場合は、
  黙って切り詰めるのではなく「一部分だけを読み込みました」と警告表示する
  （`isSheetTruncated`/`getTruncatedSheetNames`, `workbookReader.ts`）。
- いずれの検査も、保存処理（`saveWorkbook`）より前に判定するため、
  検査に落ちたファイルで既存の取込み済みデータが書き換わることはない。

空ファイル・偽装ファイル（拡張子だけxlsx）・51MBの巨大ファイルでそれぞれ
正しく拒否されること、実データ5点は従来どおり問題なく取り込めることを確認済み。

## 別紙4.3対応：書式対応付けの確認必須化

別紙原本（`docs/specs/フェーズ1_優位性強化脆弱性低減_実装指示書.md`）を再確認した上で、
4.2の次に4.3を実装した（利用者の承認済み）。

要件のうち以下は、③自動解析結果の確認画面で既に満たしていた（今回変更なし）:

- 項目ごとのファイル・シート・範囲・サンプル値・確度の表示
- 利用者による範囲の選び直し
- 確定した対応付けの学校別プロファイル保存
- シート名・見出し・列数・結合範囲が変わった場合の再確認要求

一方、「**低確度・未検出の項目がある状態では、自動作成を開始できない**」という受入条件は、
③の各ファイルごとの「確定する」ボタンが低確度・未検出項目のチェックを強制する仕組みは
あったが、それはファイル単位の保存操作を止めるだけで、画面遷移（ステッパー）自体は③を
経由せずに④以降へ自由に移動できてしまうという抜けがあった。フェーズ2（生成ロジック）は
まだ実装されていないため実害は無かったが、受入条件を明文化するため、④「自動作成の実行
状況」画面に、②の全ファイル取込み・③の全ファイル対応付け確定（`App.tsx`の
`canStartGeneration`、既存のステッパー判定ロジックを再利用）が満たされていない場合は
具体的な不足件数（例:「ファイル取込み 3/5件、対応付け確定 1/5件」）とともに開始不可を
明示するガードを追加した。将来フェーズ2を実装する際は、この`canStartGeneration`判定を
実際の生成処理の入口でも使うこと。

なお「確定・コピー・バックアップ」画面は、バックアップ機能がフェーズAの時点で既に
稼働中のため、このガードの対象外とし、常時アクセス可能なままにしている。

## 別紙4.4対応：確定前の一括検証（枠組みの明文化のみ）

別紙4.4の要件（日ごとの授業可能時数超過、固定条件競合、T列相当の予定時数との
不一致、単元進度の欠番・重複・分母超過、出力範囲の行列数不一致を重大エラーとして
検出し、1件でも残っていれば確定を無効化する）は、いずれも**自動配置後の月案データ
（フェーズB「生成ロジック」の出力）を前提とした検証**であり、フェーズBが未実装の
現時点では実際に計算するものが存在しない。別紙の章立てでは4.4は「優先度1：現在の
プロトタイプへ先に実装する対策」に含まれているが、要件の中身を精査した結果、
実質的には別紙5章「優先度2：生成ロジックと同時に実装する対策」に属する内容だと
判断した（このアプリ自身の`STEP_PHASE`定義でも、対応する「時数・競合チェック」
画面は元からフェーズB扱いになっており、矛盾しない）。

そのため今回は、利用者と合意の上で以下の対応に留めた（コードの実質的な検証ロジックは
実装していない、表示のみの追加）。

- 「時数・競合チェック」画面（フェーズBのプレースホルダー）に、実装時に検証する
  重大エラー5種・注意事項4種を一覧表示し、受入条件（重大エラーが残っている間は
  確定できない、注意事項は確認済みにできる）を明記した。まだ動作しないことも明示。
- 本格的な実装（実際の検証ロジック、問題選択時の該当箇所へのジャンプ、日付・校時・
  教科・原因・修正方法の付与）は、フェーズBの生成ロジック実装と同時に行う。

この変更はデータの読み書き・Excel解析ロジックに一切触れない表示のみの追加のため、
「開発プロセスの決定事項」のB案に基づき、利用者によるChrome確認は省略し、自己
チェック（Playwright）のみで完了とした。

## 別紙4.5対応：安全な値コピーのプレビュー（枠組みの明文化のみ）

別紙4.5（E4:Q65相当・AL4:AL65相当の値コピー、行数・列数・貼付開始セル・空白位置の
事前表示、分数の文字列保持、Clipboard API不可時のTSV/選択可能表フォールバック等）も、
4.4と同じ理由でフェーズ2（自動作成）・フェーズ4（編集）を経てできあがる月案データを
前提にした機能であり、現時点ではコピー対象そのものが存在しない。別紙の章立てでは
優先度1に含まれているが、4.4と同様、実質的には生成ロジック・編集画面と同時に実装
すべき内容だと判断した。

今回は「確定・コピー・バックアップ」画面（バックアップ機能は既に稼働中）に、将来
実装するコピー機能の要件をプレビュー表示するだけに留めた（実質的な値コピー・
Clipboard連携・TSV出力ロジックは未実装）。この変更もデータの読み書き・Excel解析
ロジックに一切触れない表示のみの追加のため、B案に基づき自己チェックのみで完了した。

## 別紙4.6対応：利用範囲と保証範囲の表示

別紙4.6の受入条件（「自動作成画面と確定画面の両方で、保証範囲を確認できる」）に
従い、以下4点の注記を、④「自動作成の実行状況」画面と⑨「確定・コピー・バックアップ」
画面の両方に共通で表示するようにした（`PlaceholderStep.tsx`の`ScopeNotice`）。

- この版は担任の月案作成支援用である
- 他学級・他教員・特別教室の最新状況を自動取得していない
- 取り込んだ固定時間割・分科資料の範囲内で競合を検査する
- 最終確定前に担当者が内容を確認する必要がある

データの読み書き・Excel解析ロジックに一切触れない表示のみの追加のため、B案に基づき
Playwrightでの自己チェックのみで完了した（④⑨双方への表示、無関係な画面への非表示、
既存のバックアップ機能・4.3ガード・4.4/4.5プレビューへの影響がないことを確認）。

## 別紙4.7対応：診断情報の書出し

不具合発生時に開発者が原因を特定しやすくするための仕組みを追加した。

- 新設`src/diagnostics/diagnosticLog.ts`: 「いつ・どの処理段階で・どの識別コードの
  エラーが・どんな日本語メッセージで発生したか」だけを記録するインメモリのログ
  （上限50件、超えた分は古いものから捨てる）。**IndexedDBには保存せず、ページを
  閉じれば消える**。児童名・学級名・元Excelのセル内容・ファイルの中身は一切記録しない。
- ファイル取込み（`fileValidation.ts`の各チェック関数、`describeParseError`）と
  バックアップ復元（`backup.ts`の`validateBackupPayload`）の既存のエラー分類に、
  開発者向けの短い識別コード（例:`FILE_EMPTY`、`PARSE_PASSWORD_PROTECTED`、
  `BACKUP_INVALID_JSON`）を追加した。**判定の基準（何を拒否するか）自体は変更していない**。
- エラーが実際に発生した際は、画面のエラーメッセージに識別コードを併記する
  （例:「空のファイルです...（識別コード: FILE_EMPTY）」）と同時に、上記の
  診断ログへ記録する。
- サイドバーに常時表示される「診断情報を書き出す」ボタンから、利用者が明示的に
  押した場合のみ、記録済みのログ・アプリ版（`APP_VERSION`）・ブラウザ情報
  （`navigator.userAgent`）・書き出し日時をまとめたJSONファイルとしてダウンロード
  できる。自動送信は一切行わない。

実データではなくテスト用データで、空ファイル・偽装ファイル・壊れたバックアップJSON・
形式違反のバックアップJSONをそれぞれ発生させ、画面に正しい識別コードが表示されること、
書き出した診断情報ファイルに5件すべての識別コードが記録され、各エントリの形が
`{timestamp, stage, code, message}`ちょうどであること、学級名・担任名・シート名等の
実データがファイル内に一切含まれないことをPlaywrightで確認済み。

## 別紙5.2対応：正解データを用いた回帰テストの整備

指示書7章の実装順どおり、4.7の次に5.2（優先度2、本来はフェーズ2の生成ロジックと
同時実装の想定だが、フェーズ1の検出・抽出ロジックに対する部分は今すぐ整備できると
判断し先行実装した）に着手した。

**サンプルファイルの扱いについて、利用者に確認して決定した事項**：お預かりした実際の
5つのサンプルファイル（固定時間割・授業時数/下校予定時刻・年間指導計画・分数一覧・
出力先ひな型）を回帰テストの正解データとして使う際、ファイル内部のプロパティ
（作成者名等のメタデータ）に利用者ご本人および同僚教員の実名が記録されていることが
判明した。セルの内容自体には児童の個人情報は含まれていなかったため、**メタデータ
（作成者情報）だけを削除し、セルの内容（学級名・教科名・時数等の実データ）はそのまま
保持したコピー**を`app/test-fixtures/`に保存する方針で合意した。

- `app/test-fixtures/`: メタデータ削除済みの5ファイル
  （`fixed-timetable.xlsx`、`class-hours-events.xlsx`、`annual-plan.xlsx`、
  `fractions-table.xlsx`、`output-template.xlsm`）。SheetJSで読み込み直し、
  `Author`/`LastAuthor`/`Company`等のプロパティ欄を空にして書き出したもので、
  セルの値・シート構成は元ファイルと完全に一致することを確認済み。
- `app/vitest.config.ts` / `app/tests/`: Vitestによる自動テスト
  （`npm test`で実行、`npm run typecheck:tests`で型チェック）。アプリ本体の
  ビルド（`npm run build`）には一切関与しない独立した設定。
- テスト内容: 5ファイルそれぞれの検出ロジック（`detectFields`）が正しい項目・確度で
  検出すること、担当学年以外の列が混入しないこと（過去に実際発生した回帰）、
  「別葉」「予定表」「分科計画」等の意図的に検出対象から外したシートが除外され
  続けること、総合的な学習の時間の3系列検出、分数が文字列のまま保持されること
  （日付への誤変換防止）、同一入力から同一結果になること（再現性）、
  ファイル種別の自動推測（`guessFileKind`）が5ファイルすべてで正しく働くこと。

**回帰テストの整備中に見つかった実際の不具合とその修正**：`guessFileKind`
（②ファイル取込み時に「このファイルの中身は○○のように見えます」と警告するための
簡易判定）が、実際の固定時間割ファイルを正しく推測できていなかった。原因は、
この関数内の正規表現`/特別?\s*教室/`が「教室」を連続した文字列として要求していたのに
対し、この学校のファイルの見出しは「特　　別　　教　　室」のように1文字ごとに
全角スペースで区切られており、一致しなかったため（`detectors/fixedTimetable.ts`側の
本体検出ロジックは`/特\s*別?\s*教\s*室/`と、文字間の空白を許容する正規表現に
既に修正済みだったが、`guessFileKind`側の独立した簡易判定はこの修正から漏れていた）。
`guessFileKind`側の正規表現を本体検出ロジックと同じ空白許容パターンに修正した。
この不具合は、固定時間割ファイルを誤った枠に取り込んでしまった場合の警告表示が
出ないだけで、取込み自体や既存の確認画面には影響しない（実害は限定的だが、
安全網が効いていなかったという点で修正した）。

## 決めた前提（他は今のところ仮運用のまま）

- ファイル種別の割当は自動確定しない。取込み画面の5つの枠にどのファイルを
  入れるかは利用者が選ぶ。中身から推測した種別と食い違えば警告するのみ。
- 学級プロファイルの同一性は「年度＋学年＋組」で判定する。
- バックアップの書き出し・復元は、本来フェーズD相当だが実装コストが低いため
  フェーズAの時点で先行実装した（対象は利用者情報・学級設定・学校別書式設定・
  取込んだファイルの構造のみ。月案の作成途中データ・確定版はまだ存在しない）。
