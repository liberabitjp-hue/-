# フェーズA実装時の前提・今後確認したい点

指示書23章・22章の方針（「勝手に固定的な業務ルールを作らず、仮定を一覧にして質問する」）
に沿って、フェーズA実装中に決めた前提と、次回以降に確認したい点をまとめます。

## 決めた前提（フェーズAの範囲内での仮の運用ルール）

1. **ファイル種別の割当は自動確定しない**。取込み画面には5つの枠（出力先ひな型／
   固定時間割／授業時数･下校予定時刻／年間指導計画／分数一覧）があり、どの枠に
   入れるかは利用者が選びます。中身から推測したファイル種別と枠が食い違う場合は
   警告を出しますが、強制的に入れ替えることはしません。
2. **学級プロファイルの同一性は「年度＋学年＋組」で判定**しています。同じ組み合わせで
   再登録すると上書き更新、年度・学年・組のいずれかが違えば別の学級として扱います。
   （担任名だけが変わった場合は同一学級として更新されます。）
3. **学校別書式設定（自動判定のマッピング）は、学年・学級に関係なくファイル種別ごとに
   1つだけ保存**しています。指示書5章の「同一学年では年間指導計画等を共通利用」を
   一歩進め、「同一学校なら書式は共通のはず」という前提を置いています。複数の学校で
   同じ端末を使う場合は、学校IDを追加する設計変更が必要です。
4. **授業時数･下校予定時刻ファイルで同じ月に複数の改訂版シート（「5月」「5月 (2)」等）が
   ある場合、シートの並び順で最後のものを採用候補**としています。これは今回のサンプル
   ファイルの並び方（新しい改訂ほど後ろに追加されている）から推測した仮ルールで、
   確認画面に一覧を表示し、必要なら選び直せるようにしていますが、常に正しいとは限りません。
5. **年間指導計画の「単元ごとの計画時数」列は、見出し語（時数など）に対応する列が
   見当たらない教科（学活・総合的な学習の時間など）について、見出し列自体のデータが
   少ない場合に隣接列を自動で探すヒューリスティック**を使っています。特に「総合的な
   学習の時間」のように1シートに複数の単元系列（本宮の米～／まゆみ小の伝統～／
   東日本大震災～、のように）が並ぶ構造では、単一の列に決め打ちできないため確度を
   「低」にとどめ、必ず利用者の確認を求める設計にしています。
6. **月別・教科別の予定時数は、出力先ひな型の「予定表」シートを一次情報源**として
   扱っています。各月シートのT列相当（予定）はこの「予定表」シートを数式で参照している
   実装だったため、二重管理を避けるために「予定表」シート側を基準にしました。
7. **バックアップの書き出し・復元は、本来フェーズD相当ですが実装コストが低いため
   フェーズAの時点で先行実装**しました。ただし対象データは今フェーズで保存している
   ものだけです（利用者情報・学級設定・学校別書式設定・取込んだファイルの構造）。
   月案の作成途中データ・確定版は、まだ存在しないため含まれていません。

## 次回までに確認したいこと

- **複数の学校での利用を想定するか**。想定する場合、学校別書式設定の保存キーに
  学校ID（または学校名）を追加する必要があります。
- **授業時数ファイルの複数改訂版シートの扱い**について、「シート順で最後を採用」で
  よいか、それとも毎回利用者に選ばせる方が安全か。
- **固定時間割ファイル内の「分科計画」表**（５年２組以外の学級（２－２、３－１等）の
  分科担当・時数も含む一覧）は、将来「複数学級を横断して分科担当者の空き状況を見る」
  機能（指示書12.3）のための参考データとして保持しておくべきか、それとも当面は
  対象学級の分だけに絞ってよいか。
- **「総合的な学習の時間」のように1シートに複数の単元系列が並ぶ教科**について、
  自動判定では1系列しか候補に出せません。マッピング画面で「この教科は複数の
  単元系列がある」と明示的に切り替えられるUIを用意するべきか、それとも
  利用者が手動で範囲を追加登録できれば十分か。
