# フェーズ1プロトタイプ 優位性強化・脆弱性低減 実装指示書

## 1. 目的

現在のフェーズ1プロトタイプを作り直さず、既存機能を維持しながら、実運用で重大になりやすい弱点を減らす。同時に、本アプリ固有の強みである次の価値を明確にする。

- 担任が毎月行う「翌月の月案・学習予定表作成」への特化
- 既存のExcel・PDF資料をそのまま活用できること
- 単元名と進度まで含めて作成できること
- 学校ごとの書式差を、利用者の確認を介して吸収できること
- 元のExcelへ値だけを安全に戻せること
- 管理者権限・常時インターネット接続なしで利用できること

本指示書は、学校全体の年度時間割編成機能を追加するものではない。現段階の製品範囲は、`担任による翌月月案作成の支援`とする。

## 2. 開発時の基本ルール

1. 新規プロジェクトへ作り直さず、現在のソースコードへ追加する。
2. コード変更前に、実装済み機能、データ構造、保存キー、起動方法、使用ライブラリを確認する。
3. 既存の学校別設定、担当学級設定、作成途中データを消去しない。
4. 保存形式を変更する場合は、旧形式を読み込む移行処理を用意する。
5. 一度に全面改修せず、下記の優先順位ごとに実装・確認する。
6. 元のExcel・xlsmファイルは読み取り専用とし、直接上書きしない。
7. 実装前に変更対象、影響範囲、確認方法を報告し、実装後にテスト結果を報告する。
8. 現行構成で実現できない項目は、無理に別技術へ移行せず、理由と代替案を示す。

## 3. 最初に行う現状診断

次の項目を`実装済み／一部実装／未実装／不明`で整理する。判定には、該当する画面、ファイル、関数、保存データ、動作確認結果を根拠として付ける。

| 診断項目 | 確認内容 |
|---|---|
| ファイル取込み | 対応形式、容量制限、破損ファイル時の動作 |
| 書式解析 | シート・列・見出しの判定方法、利用者による修正可否 |
| 保存 | 保存先、保存項目、データの版、消去時の挙動 |
| 復元 | バックアップ書出し、読込み、旧版互換性 |
| 自動配置 | 同一入力での再現性、条件競合時の処理 |
| 検証 | 時数差、行事・分科・教室重複、進度不整合の検出 |
| 出力 | コピー範囲、空白位置、分数、元ファイル保護 |
| エラー表示 | 原因、対象箇所、利用者が行う修正の表示 |
| オフライン | 外部通信・CDNがなくても動作するか |
| 個人情報 | 外部送信の有無、保存対象に児童情報が含まれないか |

この現状診断が完了するまでは、大きな機能追加を開始しない。

## 4. 優先度1：現在のプロトタイプへ先に実装する対策

以下は、現在のフェーズ1へ比較的小さく追加でき、事故防止効果が高い項目である。

### 4.1 変更前スナップショットと復元

学校別設定、担当学級設定、作成途中データを変更する直前に、直前状態を保存する。

要件：

- `変更前へ戻す`機能を用意する。
- 保存データに`schemaVersion`、アプリ版、保存日時を持たせる。
- バックアップファイルを書き出し、同じアプリで復元できるようにする。
- 復元前に、現在データを自動バックアップする。
- 読み込めないバックアップで現在データを上書きしない。

受入条件：設定変更後に直前状態へ戻せる。破損したバックアップを読み込んでも、現在データが残る。

### 4.2 ファイル取込み時の事前検査

ファイルを解析処理へ渡す前に、形式と構造を検査する。

要件：

- 拡張子だけでなく、実際にExcelとして読めるかを確認する。
- ファイル容量、シート数、使用範囲が異常に大きい場合は処理を止めて説明する。
- パスワード保護、破損、空ファイル、対象シートなしを区別して表示する。
- ファイル名だけで資料の種類を確定しない。
- 読み取りエラー時に、元ファイルや保存済み設定を変更しない。

受入条件：対応外・破損・空ファイルを投入しても画面が停止せず、原因と対処が表示される。

### 4.3 書式対応付けの確認必須化

任意書式の完全自動判定を保証せず、`自動候補＋利用者確認`を標準動作にする。

要件：

- 項目ごとに、ファイル、シート、範囲、サンプル値、判定確度を表示する。
- 低確度・未検出の項目がある状態では、自動作成を開始できない。
- 利用者が範囲を選び直せる。
- 確定した対応付けを学校別プロファイルとして保存する。
- 次回ファイルのシート名、見出し、列数、結合範囲が変わった場合は再確認させる。

受入条件：誤った自動判定を画面上で修正でき、保存後に再利用できる。構造が変わったファイルへ以前の設定を無警告で適用しない。

### 4.4 確定前の一括検証

出力前に必須検証を行い、重大エラーと注意事項を分けて表示する。

重大エラー：

- 日ごとの授業可能時数超過
- 行事、分科、特別教室の固定条件競合
- T列相当の予定時数と配置時数の不一致
- 単元進度の欠番、重複、分母超過
- 出力対象の行数・列数不一致

注意事項：

- 教員の希望条件を満たせない
- 前月傾向と異なる
- 推定配置を含む
- 校時未指定の行事を含む

要件：

- 重大エラーがある場合は`確定`を無効化する。
- 各問題に、日付、校時、教科、原因、修正方法を付ける。
- 問題を選択すると該当箇所へ移動する。
- 注意事項は利用者が確認済みにできる。

受入条件：重大エラーを残したまま完成扱いにできず、どこを直すか分かる。

### 4.5 安全な値コピーのプレビュー

元Excelへ貼り付ける前に、生成する値と範囲を確認できるようにする。

要件：

- `E4:Q65`相当と`AL4:AL65`相当を別々に扱う。
- コピー前に、行数、列数、貼付開始セル、空白位置を表示する。
- 数式、書式、マクロを出力対象に含めない。
- 分数は文字列として保持し、日付へ変換しない。
- Clipboard APIが使えない場合は、TSVダウンロードまたは選択可能表を提供する。
- コピー後も元ファイルをアプリ側から変更しない。

受入条件：既知の正解データと、出力行列数・値・空白位置が一致する。分数が日付にならない。

### 4.6 利用範囲と保証範囲の表示

ローカル版で確認できないことを、利用者に誤解させない。

表示内容：

- この版は担任の月案作成支援用である。
- 他学級・他教員・特別教室の最新状況を自動取得していない。
- 取り込んだ固定時間割・分科資料の範囲内で競合を検査する。
- 最終確定前に担当者が内容を確認する必要がある。

受入条件：自動作成画面と確定画面の両方で、保証範囲を確認できる。

### 4.7 診断情報の書出し

保守負担を減らすため、問題発生時に原因を共有できるようにする。

要件：

- アプリ版、ブラウザ版、処理日時、処理段階、エラー内容を記録する。
- 児童名や元Excelの全内容は診断情報へ含めない。
- 利用者が`診断情報を書き出す`操作をした場合だけファイル化する。
- エラー画面に、利用者向け説明と開発者向け識別コードを併記する。

受入条件：不具合発生時に、個人情報を含まない診断ファイルを作成できる。

## 5. 優先度2：生成ロジックと同時に実装する対策

### 5.1 説明可能で再現可能な配置

- 同じ入力、設定、アプリ版では同じ初期案を生成する。
- 各枠に`行事固定`、`分科確定`、`固定時間割`、`前月傾向`、`予定時数補充`、`手動変更`等の配置理由を持たせる。
- 自動配置できない場合は、条件を破って埋めず、未配置と理由を表示する。
- 必須条件と希望条件をデータ上でも分離する。

### 5.2 正解データを用いた回帰テスト

今回提供された5年2組の資料を、個人情報を含まないテストケースとして利用する。

最低限のテスト：

- 授業日、授業時数、下校時刻、行事の抽出
- 固定時間割の抽出
- T列相当の教科別予定時数
- 単元名とD列相当の計画時数
- 月をまたぐ進度
- `E4:Q65`相当と`AL4:AL65`相当の出力
- 同一入力から同一結果になること

仕様変更後は、このテストに合格してから利用者へ渡す。

### 5.3 手直しを減らす評価記録

本アプリの優位性を測定できるよう、個人情報を含まない範囲で次を記録する。

- 作成開始から確定までの時間
- 自動配置後の手動修正数
- 未解決件数
- 読取り対応付けの修正数
- 出力前検証で見つかった問題数

記録は端末内に保存し、利用者が削除・書出しできるようにする。外部へ自動送信しない。

## 6. 現段階では後回しにする対策

次の項目は重要だが、フェーズ1へ入れると複雑化や作り直しの危険が大きいため、基盤安定後に扱う。

- PDF・画像OCRの完全自動確定
- 学校全体の教員・教室・学級の同時最適化
- 複数教員のリアルタイム共同編集
- クラウドアカウント、権限、学校間データ分離
- 自動更新配布
- 修正履歴を使ったAI学習
- あらゆる学校書式への無確認対応

分科PDFを扱う場合も、初期段階では読み取り候補を一覧表示し、人が確定したデータだけを本時間割へ反映する。

## 7. 実装順

1. 現状診断と既存動作の記録
2. バックアップ・復元・保存形式の版管理
3. ファイル事前検査
4. 書式対応付け確認と構造変更警告
5. 一括検証と保証範囲表示
6. 安全な値コピーのプレビュー
7. 診断情報の書出し
8. 回帰テストの整備
9. 生成ロジックへの配置理由・未配置理由の追加
10. 時短・手直し件数の評価記録

各項目は個別に完成・確認し、複数項目をまとめて大規模変更しない。

## 8. 各実装単位でClaude Codeが報告する内容

実装前：

- 現在の関連機能
- 変更するファイル
- 変更しない機能
- 保存データへの影響
- 想定されるリスク
- 動作確認方法

実装後：

- 実装した内容
- テスト結果
- フェーズ1機能への回帰影響
- 未対応事項
- 利用者がChrome上で確認する手順

## 9. 完了条件

この改善指示書の第一段階は、次をすべて満たした時点で完了とする。

1. 誤ったファイルや書式を無確認で自動処理しない。
2. 保存データをバックアップ・復元できる。
3. 不正・破損ファイルでアプリ全体が停止しない。
4. 重大な時数・固定条件・出力範囲エラーを確定前に検出できる。
5. 元Excelを変更せず、値だけを指定範囲へ安全に移せる。
6. 自動作成結果の理由と未解決理由を確認できる。
7. 同じ入力から同じ結果を再現できる。
8. 既存のフェーズ1機能と保存データが維持される。
9. 不具合調査用の個人情報を含まない診断情報を書き出せる。
10. 5年2組の実データを用いた主要な回帰テストに合格する。

## 10. Claude Codeへ最初に渡す実行指示

> 現在のフェーズ1プロトタイプを基準に、本指示書の「3. 最初に行う現状診断」だけを先に実施してください。この段階ではコードを変更しないでください。診断結果を根拠付きの表で報告し、優先度1のうち現在の構成へ安全に追加できる最初の1項目を提案してください。新規作成、全面的な技術変更、既存保存データの初期化は行わないでください。私が診断結果と実装案を確認した後に、1項目ずつ実装してください。
